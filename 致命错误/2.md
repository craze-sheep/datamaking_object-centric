# 致命错误 2：Docker 容器被 OOM Killer 杀掉 + 系统内存严重不足

## 结论

数据生成 Docker 容器在运行期间被 Linux OOM Killer 强制终止，原因是 WSL2 实例物理内存仅 7.4GB，swap 2GB 全满，Blender 渲染进程占用约 1.6GB 物理内存后触发全局 OOM。容器使用 `--rm` 参数运行，被杀后自动移除，无残留容器可查。

## OOM Kill 事件记录

### 第一次 OOM（17:18:01）

内核日志（dmesg）：

```text
[Fri May 22 17:18:01] Out of memory: Killed process 1334096 (python3)
  total-vm:8020356kB (~7.6GB)
  anon-rss:1716644kB (~1.6GB)
  container: docker-f6670b5ec01fd08c98e5621d54f702e3c0ed0bd88d2b38178eeb91d7825685f9.scope
  task_memcg: /system.slice/docker-*.scope
```

被杀的是容器内的 Blender 渲染 Python 进程。同一时刻 OOM Killer 还连带杀死了多个系统服务：

- xdg-desktop-por (PID 47446)
- xdg-desktop-por (PID 47427)
- at-spi-bus-laun (PID 47419)
- dbus-daemon (PID 47416, 47426)
- xdg-document-po (PID 47432)
- xdg-permission- (PID 47436)
- fusermount3 (PID 47443)

这是一次严重的全局 OOM 事件，内核在 17:18:01 到 17:18:06 之间连续触发了多次 OOM Kill。

### 系统内存状态（事发时）

```text
Mem:    7.4GB 总计
Swap:   2.0GB，已全部用完
```

WSL2 分配的内存上限仅 7.4GB，而系统上同时运行了大量进程：

- VSCode Server (node)：~1GB
- Pylance (node)：~840MB
- OpenCode：~150MB × 2
- Hermes Agent：~225MB
- Hermes Gateway：~170MB
- Claude Code：~147MB
- MCP servers：~50MB × 4

加上 Docker 容器内 Blender 的 ~1.6GB，总计远超 7.4GB 物理内存。

## 受影响数据

### S2 L7/215：空目录

```text
database/S2/L7/215/
  Birth: 2026-05-22 18:59:40
  文件数: 0（完全为空）
```

该目录由脚本的 `make_dirs()` 提前创建，但随后的渲染/写入步骤未能完成。最后一个成功的样本是 L7/214（358 个文件，18:59:39 完成）。

215 是最后一个物理样本的第 3 个 view（left），对应物理样本 72。前 71 个物理样本（ID 1-213）均完整生成。

### S2 L6：33 个 sphere 滑出有限地面后下落

非 OOM 直接导致。复核后确认这不是 PyBullet 碰撞穿透，而是场景设计缺陷：S2 原始地面尺寸是 `(8.0, 6.0, 0.08)`，x 方向半长只有 `4.0m`；L6 中部分 sphere 从 `x=0` 以 `2.0-3.0m/s` 滑行 3 秒，最终 `x > 4.0`，已经离开地面边界，因此开始自由下落，表现为 `z_final < 0`。

```text
S2 L6 sphere 滑出地面统计：
  总 sphere 样本：324
  滑出地面后下落（z_final < 0）：33 个（10.2%）
  最深下落：L6/49 z=-5.86m
```

样本示例：

```text
L6/103: x_final=4.75, z_final=-1.79  (radius=0.18, speed=3.0)
L6/13:  x_final=5.09, z_final=-2.77  (radius=0.22, speed=3.0)
L6/49:  x_final=6.32, z_final=-5.86  (radius=0.22, speed=3.0)
```

修复：已将 `task/task6-脚本编写/generate_s2_dataset.py` 的 S2 地面尺寸从 `(8.0, 6.0, 0.08)` 调整为 `(16.0, 6.0, 0.08)`，x 方向半长从 `4.0m` 增加到 `8.0m`，覆盖当前 L6 速度范围下的 3 秒水平滑行距离。

## 当前系统风险

```text
当前内存状态（检查时刻）：
  Mem:   7.4GB 总计，5.3GB 已用，84MB 空闲，2.1GB buff/cache
  Swap:  2.0GB，2.0GB 已用（100%）
  可用：2.0GB（依赖 buff/cache 回收）
```

Swap 完全耗尽。如果再次运行 Docker + Blender 渲染，大概率再次触发 OOM Kill。

## 建议

### 短期：腾出内存后再跑

1. 关闭 VSCode Server（省约 2GB）
2. 关闭 OpenCode（省约 300MB）
3. 关闭不必要的 MCP server
4. 或者在 Windows 侧 `.wslconfig` 中给 WSL2 分配更多内存：

```ini
[wsl2]
memory=12GB
swap=4GB
```

修改后需要 `wsl --shutdown` 重启 WSL2 实例。

### 长期：脚本端减低内存压力

1. 渲染完一个 view 后释放 renderer，减少 Blender 内存累积。`task1` 和 `task6` 生成脚本已改为每个 view 独立 renderer，并在渲染后 unlink。
2. 对于会长距离水平运动的场景，确保地面尺寸覆盖完整运动范围，不要让对象在 3 秒窗口内滑出地面
3. 生成脚本加 `--samples-per-level` 参数支持断点续跑，避免 OOM 后从头重来

## 已做的 task 系列一致性修复

1. `task1-判断相机视角/generate_five_view_kubric.py` 和 `generate_s1_dataset.py` 到 `generate_s8_dataset.py` 均已改为每个 view 使用独立 `Blender` renderer，避免跨视角复用 renderer。
2. `task1-判断相机视角/generate_five_view_kubric.py` 和 `generate_s1_dataset.py` 到 `generate_s8_dataset.py` 均已在新 renderer 创建后调用 `replay_scene_keyframes(scene)`，确保仿真阶段写入的 keyframe 会同步给当前 renderer。
3. `task1-判断相机视角/generate_five_view_kubric.py` 和 `generate_s1_dataset.py` 到 `generate_s8_dataset.py` 均已在每个 view 渲染结束后调用 `unlink_renderer(scene, renderer)`，同时执行 `scene.unlink_view(renderer)` 并清理 `asset.linked_objects[renderer]`，避免旧 renderer 继续挂在 scene observer 或 asset 反向引用上。
4. `task1-判断相机视角/generate_five_view_kubric.py` 已加入单 view 失败清理；`generate_s1_dataset.py` 到 `generate_s8_dataset.py` 均已加入单 sample view 失败清理，减少空目录和半成品目录。
5. `task2` 和 `task4` 的脚本使用 PyBullet/TinyRenderer，不涉及 Kubric `Blender` renderer 复用；`task3` 和 `task5` 主要是文档/参数说明，没有同类渲染代码。
6. `generate_s2_dataset.py` 已将地面 x 方向尺寸加长，修复 L6 sphere 在 3 秒内滑出地面后下落的问题。
