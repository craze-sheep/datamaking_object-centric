# 致命错误 7：Docker 容器内 Blender OPTIX 无设备，静默回退 CPU 渲染

## 问题描述

WSL2 + Docker 环境下，Kubric 使用 `KUBRIC_GPU_BACKEND=OPTIX` 运行 Blender 3.6.15 渲染时，Blender 枚举不到 `OPTIX` 类型的 Cycles 设备，只有 `CUDA` 设备。原 Kubric 代码在设备列表中逐一匹配 `device.type == "OPTIX"`，全部不匹配导致所有 GPU 设备的 `use` 被设为 `False`，Blender 静默回退到 CPU 渲染，GPU-Util 始终 0%。

## 根因分析

容器内 Blender 检测设备：

```python
prefs.compute_device_type = "OPTIX"
prefs.get_devices()
print([(d.name, d.type, d.use) for d in prefs.devices])
```

结果只有：

```text
[("NVIDIA GeForce RTX 4060 Laptop GPU", "CUDA", True), (..., "CPU", False)]
```

没有任何 `type == "OPTIX"` 的设备。原 Kubric 代码（`kubric/kubric/renderer/blender.py`）：

```python
device.use = device.type == cycles_prefs.compute_device_type
```

当 `compute_device_type == "OPTIX"` 但设备只有 `CUDA` 时，`device.use` 全部被设为 `False`。scene 仍显示 `cycles.device == "GPU"`，但没有启用任何 GPU 设备，Cycles 最终走 CPU。

## 实际后果

- `nvidia-smi` 能看到 GPU，但 GPU-Util 始终 0%，显存仅 42MiB
- Blender CPU 利用率 736%，全部走 CPU 渲染
- 720×720 分辨率渲染耗时数分钟（GPU 应该秒级）
- 输出结果正确，问题完全隐蔽，只体现在速度上

## 教训

1. **GPU 后端回退不能静默**：请求 OPTIX 但没有对应设备时，必须有明确 warning 或 error，不能假装用 GPU 实际走 CPU
2. **WSL2 + Docker 下 OPTIX 设备枚举不可靠**：`nvidia-smi` 能看到 GPU 不代表 Blender 能枚举到 OPTIX 设备，需要实际验证 Cycles 设备列表
3. **验证 GPU 渲染是否生效不能只看 `nvidia-smi`**：必须同时检查 GPU-Util 和 Blender 进程的 GPU 显存占用

## 修复

已修改 `kubric/kubric/renderer/blender.py`：

- 请求的 GPU 后端无设备时打印 warning
- `OPTIX` 无设备时自动回退到 `CUDA`
- 如果连 `CUDA` 也没有可用设备，直接抛 `RuntimeError`，不再静默 CPU 渲染

验证结果：

```text
WARNING:kubric.renderer.blender:No OPTIX Cycles GPU devices detected.
WARNING:kubric.renderer.blender:Falling back from OPTIX to CUDA for Cycles GPU rendering.
INFO:kubric.renderer.blender:Using CUDA GPU Device(s): ['NVIDIA GeForce RTX 4060 Laptop GPU']
scene_device GPU
compute_device_type CUDA
devices [('NVIDIA GeForce RTX 4060 Laptop GPU', 'CUDA', True), (..., 'CPU', False)]
```

当前建议直接使用 CUDA 后端：

```bash
-e KUBRIC_USE_GPU=True \
-e KUBRIC_GPU_BACKEND=CUDA \
```

✅ 已修复 — OPTIX 无设备时自动回退 CUDA 并打印 warning，无可用 GPU 设备时抛 RuntimeError
